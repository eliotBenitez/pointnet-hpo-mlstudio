# Этап 1 ML Studio: полный сквозной pipeline

## Intent

Сделать GUI полноценным управляющим интерфейсом для основного процесса проекта:

`подбор → финальный прогон на отдельном датасете → сводный отчёт`.

Пользователь должен иметь возможность задать существенные параметры CLI, сохранить воспроизводимую конфигурацию и безопасно продолжить только совместимый study.

## Goals

- Добавить в форму запуска отдельные поля для каталога финальных данных и каталога результатов.
- Передавать эти значения в `run_all.py` и в одиночные запуски без ручного редактирования CLI.
- Сделать `loss` и `focal-gamma` явными параметрами полного сценария и проверить их передачу.
- Добавить отдельные поля `patch-points` и `patches-per-scene`.
- Сохранять параметры формирования данных в артефактах запуска и восстанавливать их при открытии прогона в форме.
- Не допускать незаметного смешивания несовместимых trials в существующем `study.db`.
- Дать понятный GUI-путь для финального прогона из параметров лучшего run.

## Non-goals

- Встроенный просмотр Markdown-отчётов.
- Новый мастер проекта или новый формат хранения результатов.
- Изменение алгоритма обучения, search space или формата существующих `best.json`, `split.json`, `trials.csv`.
- Исправление остановки process tree, подтверждений удаления и прочих задач этапов 2–3.
- Поддержка W&B как отдельного UX-потока.

## Constraints

- Русский интерфейс и существующая визуальная система из `mlstudio/DESIGN.md`.
- Файловая система остаётся источником истины.
- Старые артефакты могут не содержать новых параметров.
- `run_all.py` уже принимает `--data`, `--final-data`, `--runs`, `--loss` и `--focal-gamma`; поддержку `--patch-points` и `--patches-per-scene` нужно добавить и передать во все дочерние запуски.
- Параметры должны быть согласованы с `hpo_pointnet.py` и `predict_scene.py`.
- CLI preview должен показывать фактически запускаемую команду.

## Approaches

### 1. Расширить существующую форму и запуск — выбранный подход

Добавить поля в текущую форму, расширить построение аргументов, сохранить параметры в существующих run-артефактах и использовать текущие карточки runs/scenarios. Для финального запуска использовать существующий механизм `--fixed-params`, автоматически создавая params-файл рядом с каталогом результатов.

Плюсы: минимальные изменения, сохраняется текущая навигация и файловая модель, меньше риска расхождения с CLI.

### 2. Отдельный мастер полного pipeline

Создать новый пошаговый экран от подбора до финала и отчёта.

Минусы: дублирует форму и сценарии, увеличивает поверхность UI и не решает сам по себе совместимость study.

### 3. Оставить форму и поддержать всё через дополнительные аргументы

Не добавлять структурированные поля, а только улучшить parser аргументов.

Минусы: параметры плохо обнаруживаются, не валидируются и не восстанавливаются; это не подходит для командного воспроизводимого workflow.

## Design

### Configuration fields

В режиме одиночного запуска добавить:

- `Точек в патче` → `--patch-points`;
- `Патчей на сцену` → `--patches-per-scene`;
- `Каталог результатов` или структурированный выбор каталога, по умолчанию `runs`.

В режиме `run_all.py` добавить:

- `Данные для подбора` → `--data`;
- `Данные для финала` → `--final-data`;
- `Каталог результатов` → `--runs`;
- `Эпох в финальном прогоне`;
- общие `loss` и `focal-gamma`;
- общие `patch-points` и `patches-per-scene`.

Поле `data_dir` сохраняется для обратной совместимости, но в UI получает ясную роль. Каталоги выбираются как пути относительно корня проекта либо как абсолютные пути, если текущий интерфейс уже допускает такой ввод.

### Command construction

`command()` должен строить одинаково прозрачные аргументы для обоих режимов:

- одиночный HPO использует выбранный `--output-dir`, построенный из каталога `runs` и имени прогона;
- `run_all.py` получает `--data`, `--final-data`, `--runs`, `--final-epochs`, `--loss`, `--focal-gamma`, `--patch-points`, `--patches-per-scene`;
- при выборе `final` поле `--final-data` обязательно; при пустом поле запуск блокируется;
- preview команды и фактический запуск используют один и тот же массив аргументов.

Передача уже поддерживаемых loss-параметров проверяется тестом/ручной проверкой; не создавать дублирующую логику.

### Artifact persistence and resume

Параметры запуска, влияющие на сопоставимость study, должны присутствовать в `split.json` и/или `best.json`:

- `data_dir`;
- `seed`;
- `epochs`;
- `loss`;
- `target`;
- `features`;
- `patch_points`;
- `patches_per_scene`.

При «Продолжить в форме» GUI восстанавливает все доступные параметры. Если старый run не содержит новых ключей, UI показывает статус «параметр не записан в старом артефакте», а не молча выбирает значение.

До запуска продолжения сравниваются параметры текущей формы с параметрами run. Если несовместимый параметр отличается или неизвестен, запуск в существующий каталог блокируется. GUI предлагает вернуть параметры run или создать новый каталог; продолжение в прежнем каталоге без совпадения запрещено. `workers` не считается параметром сопоставимости и может меняться.

Эта проверка должна выполняться и в `hpo_pointnet.py`, чтобы запуск через CLI не мог незаметно смешать trials. Нельзя считать только `SEARCH_SPACE_VERSION` достаточной проверкой совместимости.

### Final run from best result

На странице run добавить отдельную кнопку `Финальный прогон`. Действие:

1. читает `best.json`;
2. создаёт `<runs>/<name>.params.json` в выбранном каталоге результатов;
3. предлагает или использует выбранный каталог финальных данных;
4. запускает `hpo_pointnet.py` с `--fixed-params`, `--n-trials 1` и заданным числом эпох;
5. пишет отдельный каталог `final_<name>`;
6. показывает точную команду и связь с исходным run.

Кнопка недоступна без валидного `best.json`, каталога финальных данных или при конфликте активного процесса.

### Validation

Проверять до запуска:

- числовые значения patch-параметров положительны;
- каталоги данных существуют или явно помечены как отсутствующие;
- каталог результатов не совпадает с активным каталогом другого процесса;
- `final-data` нужен только если выбран `final`;
- выбранный loss и gamma согласованы;
- при продолжении study параметры совместимы.

Ошибки показываются рядом с формой и в блоке команды, запуск блокируется.

### Compatibility

Старые одиночные runs продолжают открываться. Если новые параметры отсутствуют, GUI не меняет старые артефакты автоматически и предлагает задать значения/создать новый run. Формат логов и существующие имена файлов не меняются.

## Verification criteria

- Preview и фактический запуск `run_all.py` содержат выбранные `--final-data` и `--runs`.
- Полный сценарий с Focal Loss передаёт выбранные `--loss` и `--focal-gamma`.
- Значения `patch-points` и `patches-per-scene` видны в форме, preview команды и артефактах.
- Открытие существующего run восстанавливает эти параметры или явно сообщает, что их нет.
- Несовместимое продолжение не запускается в старом `study.db` без явного решения пользователя.
- Финальный запуск использует `best.json`, отдельный каталог `final_<name>` и `--fixed-params`.
- Существующие тесты Python и `cargo test` проходят.
- Изменения не затрагивают `run_all.cmd`/`run_all.ps1` и не меняют форму логов.
